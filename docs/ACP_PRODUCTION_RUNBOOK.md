# دليل تشغيل ACP Enterprise في الإنتاج

## الحالة

المستودع يحتوي على قاعدة PostgreSQL ومهاجرات Supabase، تسجيل الدخول والصلاحيات، CRUD، المزامنة دون اتصال، التقارير، الاختبارات، إعداد Vercel، ونشر آلي محكوم. يبقى ربط حسابات السحابة والدومين الفعلي مرة واحدة قبل أول نشر.

## البيئات

يُعتمد مشروعان منفصلان في Supabase:

- `ACP Staging` للاختبار وقبول المستخدم.
- `ACP Production` للبيانات الفعلية.

ويُعتمد مشروع Vercel منفصل أو بيئة Production مستقلة مرتبطة بالدومين الرسمي.

## GitHub Environment

أنشئ Environment باسم `production` وفعّل موافقة يدوية قبل النشر، ثم أضف الأسرار التالية:

| السر | الغرض |
|---|---|
| `SUPABASE_ACCESS_TOKEN` | تنفيذ Supabase CLI من GitHub Actions |
| `SUPABASE_PROJECT_ID` | مرجع مشروع Supabase الإنتاجي |
| `SUPABASE_DB_PASSWORD` | دفع مهاجرات PostgreSQL |
| `VITE_SUPABASE_URL` | رابط Supabase العام للواجهة |
| `VITE_SUPABASE_ANON_KEY` | المفتاح العام المسموح للمتصفح |
| `VITE_APP_URL` | رابط ACP الرسمي باستخدام HTTPS |
| `VERCEL_TOKEN` | النشر إلى Vercel |
| `VERCEL_ORG_ID` | معرف الفريق أو الحساب في Vercel |
| `VERCEL_PROJECT_ID` | معرف مشروع Vercel |

لا يُحفظ أي مفتاح إداري أو كلمة مرور داخل ملفات الواجهة أو GitHub.

## النشر الأول

1. شغّل Workflow باسم `Database Quality and Security` وتأكد من نجاح إعادة بناء قاعدة البيانات واختبارات pgTAP.
2. أنشئ أول مستخدم في Supabase Auth.
3. حدّث ملفه في جدول `profiles` إلى الدور `system_admin` من لوحة SQL الموثوقة.
4. شغّل Workflow باسم `Production Deployment` مع تفعيل قاعدة البيانات والدوال والواجهة.
5. اربط الدومين في Vercel، ثم أضف سجلات DNS المطلوبة لدى مزود الدومين.
6. فعّل `ACP_PRODUCTION_MONITORING_ENABLED=true` بعد نجاح الدومين لتشغيل الفحص الدوري.

## Edge Functions

يتم نشر:

- `report-qr`: توليد QR لتوثيق التقارير.
- `invite-user`: دعوة المستخدمين والتحقق من أن المنفذ مدير نظام.

يُضبط سر `ACP_APP_ORIGIN` تلقائيًا أثناء النشر ليقبل الطلبات من رابط ACP الرسمي فقط.

## النسخ الاحتياطي 3-2-1

أضف الأسرار التالية إلى Environment الإنتاج:

| السر أو المتغير | الغرض |
|---|---|
| `SUPABASE_DB_URL` | اتصال PostgreSQL مخصص للنسخ الاحتياطي |
| `BACKUP_ENCRYPTION_PASSWORD` | تشفير النسخة قبل حفظها |
| `BACKUP_S3_URI` | موقع نسخة خارجية اختياري مثل `s3://bucket/acp` |
| `AWS_ACCESS_KEY_ID` | وصول التخزين الخارجي عند استخدام S3 |
| `AWS_SECRET_ACCESS_KEY` | مفتاح التخزين الخارجي |
| `AWS_REGION` | منطقة التخزين |
| Variable `ACP_BACKUPS_ENABLED=true` | تشغيل النسخ اليومية |

Workflow النسخ الاحتياطي:

- ينشئ PostgreSQL dump مضغوطًا.
- يتحقق من إمكانية قراءة ملف الاستعادة.
- يشفره قبل التخزين.
- يحتفظ بنسخة تشغيلية في GitHub Artifacts لمدة 30 يومًا.
- ينسخ نسخة إضافية خارجية عند ضبط S3.

يجب تنفيذ اختبار استعادة ربع سنوي على بيئة Staging وعدم الاكتفاء بوجود ملفات النسخ.

## المراقبة

Workflow باسم `Production Smoke Test` يتحقق كل 30 دقيقة عند تفعيل المتغير:

- استجابة رابط النظام.
- وجود HSTS وCSP ومنع تضمين النظام داخل إطار.
- توفر Manifest وService Worker.
- صحة خدمة Supabase Auth.

## بيانات المشروع الحقيقي

تُدخل بعد نجاح Staging بالترتيب:

1. المشروع والعميل والمدينة.
2. المباني والأصول والبوابات.
3. الموظفون والتكليفات والأدوار.
4. المستودعات والأصناف والأرصدة الافتتاحية.
5. البلاغات والتقارير الافتتاحية عند الحاجة.

لا تُدخل بيانات شخصية حقيقية في ملف `seed.sql` أو داخل GitHub. الاستيراد الفعلي يتم عبر الواجهة أو أداة استيراد مؤمنة إلى بيئة Staging ثم Production.

## التراجع عند فشل إصدار

- الواجهة: استخدم Rollback من Vercel إلى آخر Deployment ناجح.
- قاعدة البيانات: لا تعدّل Migration منشورة؛ أنشئ Migration تصحيحية جديدة.
- البيانات: استعد النسخة إلى مشروع Staging أولًا، تحقق منها، ثم نفّذ خطة الاستعادة الإنتاجية المعتمدة.
